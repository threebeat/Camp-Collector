# Prompt for the next developer or AI agent

Written after implementing and validating the version-12 game changes. Copy the prompt below into a future coding session with this repository available. It is a handoff, not a requirement to adopt one permanent architecture or gameplay structure.

---

You are continuing an existing browser auto-battler/character collector for its owner. Treat this as a long-lived project that must remain understandable to future humans and agents. The final game name is undecided; “Camp Collector” is only the repository label. Do not reintroduce Frutiger Fighters, Wayward Company or Little Legends.

Read `README.md`, `docs/CURRENT_GAME.md`, `docs/ARCHITECTURE.md`, `docs/CONTENT_GUIDE.md`, `docs/VISION.md`, `docs/DEVELOPMENT.md` and `docs/RELEASE_NOTES.md` before proposing broad changes. Use `docs/CONTENT_REFERENCE.md` for current inventories and formulas. These describe the present implementation and intentions, not an immutable design. Inspect the current checkout and the owner's newest feedback; do not treat old conversation proposals as all still active.

Version 12 added Camp capacity/cabins and release, Archaeology/egg/fossil companions, Blacksmith weapon services, three mini-bosses per map, geography-driven roads, fixed 1× direct routes and rewarding detours, today-only Daily Battle, configurable NPC difficulty and boss champions, cosmetic previews/full guises, original authored Mythicals, clearer battle outcomes, smoke/hairless race art and short base weapon names. Its baseline is 130 passing tests, successful build/artifact validation and inspected native asset sheets. Actual phone/browser layout QA is still outstanding. Run `npm ci`, `npm test`, `npm run build` and `npm run validate` in Node 24+ to establish your baseline.

The owner explicitly requested the v12 reset. Current saves use `camp-collector-v12` and season `camp-fresh-2026-10-11`; the appended `0001_fresh_camps` migration wipes the old shared challenge board. Do not reset again unless newly authorized. Preserve character IDs, names, favorites, bonds, journals, belongings, earned rewards and active-party checkpoints through future changes. Database migrations are append-only. Never commit actual player saves or credentials.

The existing private Site is bound by `.openai/hosting.json`; preserve its audience, project and deployment origin. GitHub is connected as `threebeat`, but creation of the proposed private `threebeat/camp-collector` was not available to the previous agent. Verify whether the owner has since created/connected it and complete the prepared source transfer if possible. Do not claim a repository or deployment exists until verified. Ordinary Git and local running must remain possible without AI. Keep source/docs/history recoverable, and report any concrete access blocker.

The owner's main aim is attachment to a persistent, increasingly unique company. Favor readable mobile scenes, meaningful visible upgrades, understandable automatic combat, fair background progression, valuable recruitment and a Camp that feels like home. The owner is open to changes in gameplay and structure; explain why a proposed change supports those aims and implement a focused, testable improvement rather than choosing a permanent framework or roadmap on their behalf.

Promising improvement directions, to prioritize against the owner's current request:

1. Test real phone portrait layouts, touch drag/drop and tap alternatives, service sheets, map fitting/route selection, inspector overlays, result timing, reduced motion and accessibility. The DOM tests cannot prove these layouts work.
2. Improve persistence and background play. Personal saves/economy are browser-local; a Web Worker advances open-page parties, then missing time catches up at 1× on reopening. There is no continuously executing expedition server or cross-device Camp save. Design authenticated durable saves, idempotent rewards and multi-tab/device handling before promising more. Compare timestamp-based progression with server simulation based on actual cost/fidelity needs.
3. Strengthen the shared challenge economy. Battles and snapshots are server-resolved/sanitized, but client-owned gold and collections cannot prove legitimate ownership. Server-owned transactions/receipts are more valuable than merely adding numeric input checks.
4. Measure first-hour pacing: first journey survival, fourth-recruit cost, food flow, Camp unlocks, XP/class points, transformation materials and gem sinks. Make character and equipment choices affect actual behavior; avoid replacing memorable recruits with endless interchangeable drops.
5. Refactor the broad `app.js`, `data.js` and `progression.js` files incrementally. Separate canonical content, compatibility handling, services and screens while preserving saves and deterministic combat. The current narrow concatenation build also deserves a robust module strategy if backend dependencies grow.
6. Deepen original content and visual identity: distinct race physiology, coherent Mythical mechanics, more varied armor/pets, geography-specific bosses, contextual dialogue/journals and clearer before/after upgrades. Keep item art consistent on cards and battlefield units. Update acquisition, restrictions, combat, serialization, Codex and generated reference together.

After changes, run appropriate tests/build validation and use supported browser QA when available. Keep the docs current, describe what changed and why, distinguish actual verification from assumptions, publish the verified source when authorized, return working links and leave an updated handoff. Carry necessary work through to completion; if access blocks a final action, finish everything independent of that access first and identify the exact remaining step.
